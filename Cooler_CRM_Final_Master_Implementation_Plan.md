# Cooler CRM / After-Sales Service Management System
## Final Master Implementation Specification

**Document purpose:** This is the source-of-truth specification for an AI coding agent to design and develop the Cooler CRM / After-Sales Service Management System.

---

## 1. Product Vision

Build a modern, original CRM and after-sales service management platform for a cooler company.

The system will manage the complete service lifecycle:

**Complaint Creation → Service Center Selection → Technician Assignment → Visit Scheduling → Diagnosis & Work → Parts → Resolution Submission → Service Center Review → Admin Customer Confirmation → Happy Code Verification → Final Closure**

The product is an internal operations platform. There is **no customer login, customer portal, or customer app in MVP**.

The design must be original and modern. Do **not** copy or imitate any competitor screenshot or UI.

---

## 2. Locked Business Rules

These rules are considered final unless explicitly changed later.

1. Only Admin can create complaints.
2. Admin manually selects the final service center.
3. The system may recommend nearby/eligible service centers, but it must never auto-assign.
4. Service Center Owner can create and manage technicians belonging to that center.
5. Service Center Owner can assign/reassign technicians and schedule/reschedule visits.
6. Technician can work only on complaints assigned to that technician.
7. Technician cannot final-close a complaint.
8. Service Center Owner cannot final-close a complaint.
9. Admin performs final customer confirmation and closure.
10. Happy Code is generated by the system and verified by Admin before closure.
11. No WhatsApp API in MVP; use a WhatsApp deep link with a prefilled message.
12. No SMS, email, push, or automatic notification system in MVP.
13. No GPS tracking.
14. Customer does not have an account.
15. Old complaints must never be overwritten.
16. Repeat complaints must preserve complete previous service history.
17. No hard delete for important operational records; use active/inactive or archival logic.
18. Backend permissions and status transitions must be enforced server-side, not only in UI.

- Disable the WhatsApp action.
- Show a clear reason.
- Allow Admin to correct the number.

## 7. Simplified Status Workflow

Visible statuses should remain simple while detailed actions/events are captured in the timeline.

Final status set:

1. NEW
2. ASSIGNED
3. TECHNICIAN ASSIGNED
4. VISIT SCHEDULED
5. IN PROGRESS
6. WAITING FOR PARTS
7. REVISIT REQUIRED
8. RESOLUTION SUBMITTED
9. ADMIN CONFIRMATION
10. CLOSED
11. REOPENED
12. CANCELLED

Status transitions must be validated by backend rules and role permissions.

### End-to-end flow

`NEW`
→ Admin selects Service Center
→ `ASSIGNED`
→ Service Center assigns Technician
→ `TECHNICIAN ASSIGNED`
→ Visit scheduled
→ `VISIT SCHEDULED`
→ Technician starts visit
→ `IN PROGRESS`
→ Work/parts/diagnosis
→ `RESOLUTION SUBMITTED`
→ Service Center review
→ Accept → `ADMIN CONFIRMATION`
→ Admin calls customer
→ Happy Code verified
→ `CLOSED`

If resolution is insufficient:
→ `REVISIT REQUIRED`
→ technician rework/revisit
→ resolution submitted again.

If parts are unavailable:
→ `WAITING FOR PARTS`
→ parts become available
→ work resumes.

## 13. Repeat Complaint Logic

If the same problem repeats:

Admin should see prior complaint/service history and choose:

**Reopen Existing Complaint**

The original complaint is preserved and closure history is retained.

If the issue is a genuinely new problem:

**Create New Complaint**

The new complaint must show previous service history for the same customer/product/serial number.

### Important rule

Never overwrite an old complaint.

MVP should not use automatic AI duplicate detection.

Use human decision-making with strong history visibility.

### Serial number history

Searching a serial number should prominently show:
- Previous complaints
- Dates
- Problems
- Resolutions
- Parts used
- Reopens

## 19. Technical Rules for AI Development Agent

### Architecture

Use a clean, modular architecture suitable for long-term maintenance.

Recommended structure:
- Frontend
- Backend/API
- Relational database
- File/object storage for attachments
- Authentication/authorization layer

### Security

- Passwords must be securely hashed.
- Enforce RBAC on backend.
- Validate all input server-side.
- Never trust client-side permissions.
- Restrict complaint queries by service_center_id / technician_id.
- Restrict attachment access.
- Use secure Happy Code generation and verification.
- Protect against unauthorized status transitions.
- Record important actions in audit logs.

### Database

Use:
- Foreign keys
- Appropriate indexes
- Unique constraints
- Transactions where multiple records must change together

Important indexes:
- Complaint number
- Customer mobile
- Serial number
- Product/model
- Status
- Priority
- Service center
- Technician
- Created date
- SLA state

### Data integrity

- No hard deletion of operational history.
- Use active/inactive flags for masters.
- Preserve all complaint history.
- Use transactions for:
  - Complaint closure
  - Parts issue/usage
  - Reassignment
  - Reopen actions

### Files

Attachments must:
- Have access control.
- Be associated with complaint/visit.
- Store metadata.
- Validate file type/size.
- Not be publicly accessible by default.

### Performance

- Pagination for large lists.
- Server-side filtering/search.
- Indexed queries.
- Avoid loading all complaints into browser.
- Use reusable components.
- Keep technician PWA lightweight.

### Time

Use consistent server-side timestamps and a clear timezone policy.

## 23. End-to-End Workflows

### Workflow A — New complaint

1. Admin opens Create Complaint.
2. Search/select customer.
3. Search/select product/model.
4. Enter serial number.
5. Enter complaint details.
6. Select priority.
7. Select warranty.
8. Confirm service address.
9. System recommends eligible service centers.
10. Admin manually selects service center.
11. System creates unique complaint number.
12. System generates Happy Code.
13. Complaint becomes NEW/ASSIGNED according to assignment transition.
14. Admin can click WhatsApp and send prefilled message manually.

### Workflow B — Service center assignment

1. Service center sees assigned complaint.
2. Owner reviews complaint.
3. Owner selects technician.
4. Technician receives job through dashboard.
5. Status becomes TECHNICIAN ASSIGNED.

### Workflow C — Technician visit

1. Technician opens job.
2. Technician calls customer if needed.
3. Technician starts visit.
4. System records visit timestamp.
5. Technician records customer availability.
6. Technician enters diagnosis.
7. Technician records work performed.
8. Technician records parts.
9. Technician uploads optional photos.
10. Technician submits resolution.

### Workflow D — Parts unavailable

1. Technician identifies required part.
2. Technician requests part.
3. Service center reviews request.
4. If unavailable, complaint moves/remains WAITING FOR PARTS.
5. Once available, part is issued.
6. Technician resumes work.
7. Actual usage is recorded.
8. Stock is decremented on finalized usage.

### Workflow E — Revisit

1. Service center reviews resolution.
2. Resolution is insufficient.
3. Owner selects Revisit Required.
4. Reason is mandatory.
5. Technician receives/reviews revisit job.
6. Technician performs additional work.
7. Technician submits resolution again.

### Workflow F — Final closure

1. Service center accepts resolution.
2. Complaint moves to ADMIN CONFIRMATION.
3. Admin calls customer.
4. Admin confirms service outcome.
5. Admin asks for Happy Code.
6. Admin enters/verifies code.
7. If valid, Admin closes complaint.
8. Closed timestamp is stored.
9. Full timeline remains available.

### Workflow G — Repeat issue

1. Admin searches customer/serial number.
2. System shows service history.
3. Admin determines whether issue matches previous complaint.
4. If same problem → Reopen Existing Complaint.
5. If new problem → Create New Complaint.
6. Previous history remains visible.

## 28. Final Product Definition

The final MVP is an internal after-sales service operations platform with three roles:

**Admin → Service Center Owner → Technician**

The central object is the **Complaint**.

The system must provide complete traceability from complaint creation to final closure:

**Customer + Product + Complaint → Service Center → Technician → Visit → Diagnosis → Work → Parts → Resolution → Review → Admin Confirmation → Happy Code → Closure**

The product must be:

- Modern
- Original
- Responsive
- Secure
- Role-based
- Audit-friendly
- Scalable
- Easy for Admin/Service Center teams
- Extremely simple for field technicians

The final closure authority always remains with **Admin**.
